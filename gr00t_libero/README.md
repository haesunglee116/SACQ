# GR00T–LIBERO integration

This directory provides the model integration and explicit pipeline commands.
Use the [published calibration manifest and dataset guide](../data/libero_calibration/README.md)
for the selected observations, and [Capture and teacher inputs](CAPTURE_INPUTS.md)
for the serialized format. Observation archives are distributed separately;
model checkpoints, teacher caches and simulator assets are external inputs.

For simulator-free BF16/SACQ A16 action generation, use the
[single-request inference guide](INFERENCE.md). It includes a portable input-bundle
exporter; the new entrypoint still requires GPU validation and model artifacts.

## Included

- Transitive local Python helpers for the selected fitters, allocator, index
  worker, calibration worker and final rollout worker.
- Modified model-runtime overlays and the original checkout dependency manifest.
- Layer-role/candidate metadata (not calibration captures).
- A source materializer and explicit five-stage command runner.
- Path-explicit fitting/allocation adapters. DiT fitting uses the supplied suite
  checkpoint instead of silently falling back to Spatial; missing aware metrics
  raise an error instead of switching to Euclidean fitting.

`SOURCE_MANIFEST.json` pins original and exported sources. Helper-only extracts
exclude unrelated cloud/scheduler launchers. `UNRESOLVED_IMPORTS.json` inventories
external packages; static closure does not prove runtime dependency completeness.

For the order of commands and stage handoffs, see [Execution runbook](RUNBOOK.md).
It distinguishes required user inputs from files generated by this release.

See [Capture and teacher inputs](CAPTURE_INPUTS.md) for the serialized request
contract, order-dependent split/noise, and the distinction between caches and
calibrated checkpoints.

See [Runtime environments](ENVIRONMENT.md) for the separate core, policy and
simulator dependencies, including the additional HQQ dependency.

## Prepare sources

```bash
python gr00t_libero/pipeline.py catalog
python gr00t_libero/pipeline.py prepare --workspace /absolute/new/workspace
```

Preparation writes into a NEW directory and never overwrites an existing tree.
It substitutes the neutral `@WORKSPACE@` marker, checks source hashes and records
the resulting hashes. It does not download models, select data, install packages,
start GPUs or assert that an experiment is ready.

If a local GR00T Git checkout already contains the reference revision, use:

```bash
python gr00t_libero/pipeline.py prepare --workspace /absolute/new/workspace \
  --gr00t-checkout /absolute/existing/GR00T-checkout
```

This exports public upstream commit `4b1dca9d88d2a0b9ea5a65aa61c82ff89f5c4f0e` into the new
workspace and then applies the bundled local overlays. It reads committed files,
not mutable working-tree changes or untracked files, and leaves the source
checkout unchanged. The resulting receipt includes hashes of upstream files and
the overlaid versions, plus the upstream revision. It does not fetch missing
commits, install dependencies, initialize submodules, download model assets, or
copy the checkout's `.git` directory. Internal symbolic links to regular files are materialized as file contents.
External, missing, cyclic or directory link targets fail explicitly.

The GR00T checkout's `pyproject.toml` specifies Python 3.10 and its model
dependencies. Install its runtime and the simulator environment separately;
the small-core CPU test environment is NOT a substitute. Preparation without
`--gr00t-checkout` stages only the bundled helpers/overlays, as before, and is
not a complete GR00T checkout.

Obtain GR00T from `https://github.com/NVIDIA/Isaac-GR00T.git` and LIBERO from
`https://github.com/Lifelong-Robot-Learning/LIBERO.git`. The repositories must
contain the pinned revisions; a shallow clone of a newer head may not contain
them. The earlier local preparation used research-fork commit
`63ff416404087491ee09cf2563b54744d099d6ec`; that private-fork dependency has been
replaced by the public ancestor plus the bundled runtime overlays. Unrelated
research archives and optional rotated/Hadamard, TAC, tracing and OFT experiments
from that fork are not supported entrypoints in this release.

For the simulator, also pass a local Git checkout containing LIBERO commit
`8f1084e3132a39270c3a13ebe37270a43ece2a01`:

```bash
python gr00t_libero/pipeline.py prepare --workspace /absolute/new/workspace \
  --gr00t-checkout /absolute/GR00T-checkout --libero-checkout /absolute/LIBERO-checkout
```

This exports both pinned commits and applies the 13 exact tracked research
LIBERO Python changes plus their required object-definition module, listed in
`LIBERO_OVERLAY.json`. It records hashes for
the exported source/assets and overlays. Mutable local files, untracked extra
tasks/assets and Git history are not copied. A helper-only preparation or
preparation without `--libero-checkout` is insufficient for simulation. The
overlay retains additional task class definitions for source fidelity; only
the four original suites are supported by this release.

## Explicit command configuration

The driver accepts a JSON configuration with this shape (placeholders below are
documentation, not an executable paper preset):

```json
{
  "schema": "sacq_gr00t_libero_execution_v1",
  "workspace": "/absolute/prepared/workspace",
  "python": "/absolute/model-environment/bin/python",
  "protocol_manifest": {"path": "/absolute/protocol.json", "sha256": "REQUIRED"},
  "stages": {
    "fitting": {"commands": [], "inputs": [], "outputs": []},
    "allocation": {"commands": [], "inputs": [], "outputs": []},
    "index": {"commands": [], "inputs": [], "outputs": []},
    "calibration": {"commands": [], "inputs": [], "outputs": []},
    "evaluation": {"commands": [], "inputs": [], "outputs": []}
  }
}
```

Each command contains a catalog `entrypoint`, explicit string `argv`, and optional
`env`. Calibration can use an explicit `launcher` beginning with
`["-m", "torch.distributed.run"]`; process count is not inferred. Each input is
`{"path": "...", "sha256": "..."}`. Outputs are exact file paths, not globs.

An input produced by an earlier stage can instead use
`{"from_stage": "fitting", "path": "/absolute/output/file"}`. Its digest is
resolved from that stage's COMPLETE receipt and checked against the actual file.
Every command's job JSON or `--stage-config` JSON must have an absolute path and
must itself appear in the stage's hashed inputs. The driver checks required top-level worker fields and artifact-record structure.
This is not a complete model/runtime or scientific-protocol validation. Fitting accepts only
`metrics`/`vlm`/`dit` operations; allocation accepts only `allocation`.

Prepare downstream jobs after their upstream artifacts exist. Keep the top-level
`protocol_manifest` immutable: changing it invalidates earlier stage fingerprints.
When a generated rollout plan must be registered after calibration, the stage
may supply its own hashed `protocol_manifest`. Its JSON must equal the base
protocol except that `inputs` can append existing absolute path/SHA-256 references.
Original inputs must remain in order, and scientific settings, sample audit,
approval declarations and all other fields must remain identical. Each added
file hash is checked. Use that extension as the rollout root's actual protocol,
as required by the pinned worker; this facility does not create authorization or
an execution receipt. Earlier stages keep their original protocol and completion
receipts. Changing scientific settings requires a separate experiment contract,
not this input-only extension.

For execution managed by this public driver, set top-level
`manage_evaluation_receipts: true`. The rollout root's `protocol.json` must be
byte-identical to the checked stage protocol. After prerequisite checks, the
driver acquires a root lock and writes the pinned worker's required
`EXECUTION_RECEIPT.json` for the actual invocation interval. It records RUNNING,
then FINISHED after workers and declared outputs succeed, or FAILED on a caught
error. These are process states, not sample approval or success-rate audits.
Existing RUNNING records, externally owned receipts and different-protocol
receipts are not overwritten. Abrupt process death can leave RUNNING; establish
that its process tree is terminal before resolving the record and retrying.
Without this explicit option, the legacy external-launcher receipt requirement
is retained. Do not create a handwritten RUNNING file to bypass that requirement.

Fitting and allocation use `release_stage.py --stage-config <JSON>` followed by
the original worker arguments. The stage JSON supplies:

| Operation | Required path bindings |
|---|---|
| `metrics`, `vlm`, `dit` | `workspace`, `processor`, `checkpoint`, `operation` |
| `allocation` | `workspace`, `processor`, four-suite `models`, exactly one of `bank` or `bank_manifest`, `allocation_requests`, `allocation_work`, `operation` |

Exactly one `--stage-config <JSON>` is accepted; abbreviated options are disabled.
With `bank_manifest`, allocation preflight checks the original candidate/rate/suite
coverage through exact manifest lookups, file hashes and codebook sizes. It does
not require historical directory names. The legacy `bank` directory mode retains
the original naming rules. This changes artifact resolution, not allocation's
objective, candidate ladder, request order or update rule.
The job workspace must match the workspace whose staged sources were checked.
Evaluation requires the plan hash to appear in the original authorized protocol,
and the task argument must match the plan.

The DiT fitter accepts explicit `strict_metrics` and `checkpoint` arguments.
The checkpoint is bound inside the fitter after CLI parsing, so the historical
suite default cannot overwrite the adapter-selected path. The adapter calls
these arguments directly rather than rewriting source at runtime.

The original fitting flags must explicitly select metric v2 and the candidate
layer set. Allocation's spawned workers inherit the same stage configuration.
The index/calibration/evaluation workers consume their explicit job/plan JSONs;
these are not interchangeable and must bind stage outputs to the next stage.

The protocol manifest must contain `benchmark: "gr00t_libero"`,
`scientific_settings_complete: true`, a sample-audit status, and a hashed
`sample_audit_receipt`. Permitted audit statuses are `PASS_DISJOINT` or
`APPROVED_DIAGNOSTIC_ONLY`; the latter also requires `diagnostic_only: true` and
`held_out: false`. For the public `sacq_sample_audit_v1` receipt, the driver
recomputes separation and coverage from its hashed manifests before execution.
See [input preparation](CAPTURE_INPUTS.md) for the audit command. Historical
externally supplied receipt formats remain hash-bound declarations; the driver
does not independently interpret them or establish their scientific approval.

```bash
python gr00t_libero/pipeline.py check --config execution.json --stage fitting
python gr00t_libero/pipeline.py run --config execution.json --stage fitting
# Then allocation, index, calibration and evaluation, in that order.
```

Stages do not advance after failure. Caught launch errors, nonzero exits and missing
outputs record `FAILED` with the error and command index. Abrupt process death
(e.g. SIGKILL or node loss) can still leave a stale `RUNNING` receipt; this driver
is not a background scheduler or liveness monitor. Prior output hashes and each prior stage's
own configuration fingerprint must match before a downstream stage can run.
Adding future-stage inputs does not invalidate already completed stages.
Receipts from older versions without stage fingerprints must not be reused.
A COMPLETE driver receipt
means process exit and declared-output checks passed, not that success rates
or numerical equivalence have been independently audited.

## Build index and calibration jobs

`jobs.py` connects an explicitly selected allocation and bank to the pinned
index worker, joins completed index shards into a calibration job, and connects
completed calibration overlays to an explicit evaluation plan. It uses
only the Python standard library. It does not fit weights, choose a checkpoint,
select development samples, authorize a protocol, or submit a job.

```bash
python gr00t_libero/jobs.py index --spec /absolute/index-spec.json --output-dir /absolute/new/index-job
python gr00t_libero/jobs.py calibration --spec /absolute/calibration-spec.json --output-dir /absolute/new/calibration-job
```

Each output directory must be new. It receives `job.json` and `inputs.json`.
Use the generated job path as the worker argument and the entries in `inputs.json`
as the stage's hashed inputs. Declare the expected worker outputs explicitly in
the execution configuration; the builder does not guess completion paths.
Model/processor directories are checked for existence, not recursively hashed.
Their immutable identities still belong in the scientific protocol.

Both specs require the following explicit fields:

| Field | Content |
|---|---|
| `schema` | `sacq_worker_build_v1` |
| `workspace` | Prepared workspace path |
| `job` | Worker-specific fields listed below |
| `trainer`, `allocation` | File references: `{ "path": "/absolute/file", "sha256": "..." }` |
| `artifacts` | Selected bank records with `layer`, `scope`, `k`, `path`, `sha256` |
| `gptq` | Frozen background records with `layer`, integer `bits`, `path`, `sha256` |

`job` always supplies `out`, `model`, and `processor`. All paths are absolute.
The CSV must have unique `layer,scope,k` rows. Bank records must exactly match
its codebook candidates. Scalar sentinels `80000`/`90000` mean 3/4-bit frozen
background in the **pinned legacy worker**; they are not a generic SACQ format.
Neither background quantization nor request captures are generated by this tool.

For **index**, also provide `target_layers` (an explicit list of unique selected
codebook layers) and `records` (file references with their original integer
`position`). The positions are preserved because the worker derives noise seeds
from them. A shard selects layers, not a new request subset; provide the approved
request list unchanged to each shard. Splitting layers does not split calibration
observations automatically.

For **calibration**, `job` also supplies `local_qa`, `batch_cache`, `local_output`,
`suite`, `tag`, and `training`. Supply `cached_launcher` as a file reference, `all_records` as
request file references in the approved original order, and `index_shards` as:

```json
[
  {
    "job": {"path": "/absolute/index-job/job.json", "sha256": "..."},
    "completion": {"path": "/absolute/index-output/COMPLETE.json", "sha256": "..."}
  }
]
```

The builder requires completion receipts belonging to those exact index jobs,
unchanged allocation/model/bank bindings, identical explicit index-correction
settings across shards, complete non-overlapping layer coverage,
and hashed index-only outputs. It retains each layer's original scope and K while
replacing its artifact path with the corrected bank path. Counts are derived from
the supplied layer lists. The original bank is not overwritten.

These are structural preparation checks, not proof of payload tensor contents,
approved sample identities, or runtime compatibility. The pinned model installer
still expects its original 338-layer allocation layout, and the evaluation installer retains the original fixed background installation.
Its SACQ layer counts and frozen-layer precision now come from the calibration
manifest, rather than a single 1.5-bit run.
The builder does not generalize that model layout. Their existing
`COMPLETE_DIAGNOSTIC` status is preserved; no held-out approval is manufactured.

## Explicit calibration settings and callback

Calibration now imports the trainer normally and calls an explicit
`install_background(policy, trainables, device)` hook after quantized-layer setup
and before resume/optimizer construction. `local_output` is passed explicitly
as the trainer output directory. Local and durable output may be the same
directory without truncating the saved checkpoint. It no longer rewrites Python source
strings. The trainer's numerical body is checked against the submitted AST with
only this callback and the optional output-path binding removed.

Every calibration job must provide `training` with all fields below. Missing or
unknown fields are errors. The builder checks the positional validation split,
request count, batch divisibility and possible update budget.

```json
{
  "limit": 640,
  "epochs": 12,
  "global_batch": 6,
  "codebook_lr": 0.0001,
  "scale_lr": 0.00001,
  "val_every": 10,
  "steps_per_invocation": 0,
  "fp32_codebook_grad": true,
  "resume": true,
  "expected_updates": 1152
}
```

These values are a transcription of the **submitted worker**, also stored in
`profiles/legacy_calibration.json`. They are not an approved universal paper
preset. `steps_per_invocation` maps to the original `--steps`: zero means no
per-invocation early stop; a positive value counts newly executed updates, not
total resumed updates. `expected_updates` is the explicit completion check.
The trainer retains its original AdamW implementation, positional split, fixed
teacher/action noise and validation selection. Changing the fields is a protocol
change, not just an operational optimization.

`TRAINING_COMPLETE.json` now records the exact job hash, completed update count,
and hashes of `vlm`, `dit` and `best_state` outputs. Older completion records
without those output references need an evidence-backed manifest before the
new evaluation builder can consume them; no provenance is guessed.

## Prepare an evaluation plan

First align the installation directives with the actual calibrated allocation.
Do not reuse a previous allocation's force-bit files unchanged. The pinned
compiler has different selectors for the two scopes: a VLM codebook must have
**no force entry** so the installer's global selector 2 applies; a DiT codebook
uses the **16** BF16-or-packed sentinel. Neither selector reports nominal BPW.
The evaluation builder rejects conflicting codebook force entries before GPU work.

Create a specification with schema `sacq_installation_specs_v1`, hashed file
references `calibration_job` and `allocation`, and `templates` containing explicit
`vlm` and `dit` file references. Templates preserve installation directives for
fixed background outside the allocation. Empty templates are valid only when
that absence is appropriate for your selected runtime; the tool does not infer
background policy. Allocation rows must match the calibrated codebook selection
or scalar background precision.

```bash
python gr00t_libero/installation_specs.py --spec /absolute/installation-inputs.json \
  --output-dir /absolute/new/installation-specs
```

The output `result.json` contains `calibration.vlm_spec` and
`calibration.dit_spec` references for the evaluation builder below. It also writes
the two text files and hashed source `inputs.json`. It neither edits weights nor
changes K, quantization scope, nominal precision or authorization.

```bash
python gr00t_libero/jobs.py evaluation --spec /absolute/evaluation-spec.json --output-dir /absolute/new/evaluation-job
```

The spec uses `schema: "sacq_worker_build_v1"`, `workspace`, a hashed `tasks`
reference to the explicit root's `tasks.json`, and the complete worker `plan`.
All model/checkpoint, runtime, simulator, noise, reset, task and protocol fields
must already be supplied. `sources` must include hashes of the worker and
simulator files. The accepted rollout contract is documented in
`profiles/legacy_rollout.json`: this adapter remains the original seed17 worker,
not a newly validated multi-seed evaluator.

For `condition: "sacq"` (`"sacq1.5"` is retained as a legacy alias), also supply `calibration` with hashed references
named `job`, `completion`, `vlm_spec`, and `dit_spec`. The builder takes `vlm`
and `dit` overlays from that completion record and the frozen background from
the calibration job. It also carries the explicit expected SACQ/background
layer counts and checks each frozen payload against its declared precision,
instead of hardcoding one run’s 337/105 counts. It checks checkpoint, processor,
suite and update count and builds `workshop_model`; do not supply that derived field in `plan`.
For `condition: "bf16"`, no calibration overlay is accepted.

Preparation preserves the supplied `rollout_authorized` value; it never creates
an execution receipt, reset audit, saved noise, tasks or episode identities.
The rollout and simulator use materialized static functions with explicit
profiling/acceleration arguments. Their operation sequences are checked against
the formerly assembled functions. No runtime `inspect.getsource`/`exec` remains
in the active calibration, rollout or simulator wrappers. The original template
files remain available and pinned for provenance.

The resulting plan hash must still be registered in the actual authorized
protocol before the existing worker can execute it. This separation prevents
preparation from manufacturing approval or promoting diagnostic evidence to
held-out results.

## Aggregate only the declared evaluation episodes

```bash
python gr00t_libero/results.py --manifest /absolute/expected-episodes.json --output /absolute/new-summary.json
# Add --allow-partial only for an explicitly labelled progress report.
```

The input has `schema: "sacq_episode_results_v1"`, a condition `label`, an explicit
`aggregation` (`episode_micro` or `task_macro`), and `samples`. Each sample supplies
an absolute result `path` and an `expected` object with exactly these identities:
`method`, `suite`, `task`, `base_seed`, `policy_seed`, `episode_id`, `n_envs`,
`protocol_sha256` (the individual plan hash stored by the worker).

The tool never discovers samples by globbing a results directory. It rejects
repeated identities, wrong seeds/plans, non-boolean success values and incomplete
episode records. Missing episodes block final aggregation. With `--allow-partial`,
`success_rate_pct` stays null and the partial completed-only rate is reported
separately as `completed_success_rate_pct`; missing episodes are never counted as
failures. Task-macro averages task/seed groups equally, whereas episode-micro
weights all completed episodes equally. The manifest must explicitly select the
intended rule. This tool does not verify benchmark-wide task coverage or promote
an experiment's scientific evidence status.

## Explicit fitted-bank inventory

Allocation can use `bank_manifest` instead of the legacy `bank` directory. This
avoids historical filename conventions and directory fallbacks. The manifest
reference is `{ "path": "/absolute/bank.json", "sha256": "<file digest>" }`;
register that same file reference in the allocation stage's hashed `inputs`.
The inventory format is:

```json
{
  "schema": "sacq_packed_bank_v1",
  "artifacts": [
    {
      "scope": "vlm",
      "layer": "<exact model layer name>",
      "k": 16,
      "suite": "shared",
      "init": "aware",
      "path": "/absolute/fitted-candidate.pt",
      "sha256": "<artifact digest>"
    }
  ]
}
```

This is a format example, not a recommended codebook size or experiment preset.
Include every candidate that the approved allocation requests. Each candidate
identity `(scope, layer, k, suite, init)` must be unique. VLM entries may explicitly
use `shared`; DiT entries must name their suite. Shared and suite-specific entries
for the same VLM candidate cannot coexist. Missing entries fail rather than
selecting a candidate from another directory. Checksum checks are cached only
while the file's identity, size and timestamps remain unchanged.

`python gr00t_libero/bank.py --manifest /absolute/bank.json` checks the inventory's
file checksums. Optional `--check-payloads` deserializes **trusted local files**
and checks codebook sizes. Neither command supplies scientific authorization or
selects a protocol. The legacy directory mode remains available for archived
layouts. Fitting math, allocation decisions, and candidate selection parameters
are unchanged by this path-resolution adapter.


## Calibration cache ownership

The public calibration worker binds `out` and `local_output` to the exact job
JSON digest before loading models. Use fresh output directories for a new job,
separate from the directory that stores `job.json` and `inputs.json`. Repeating
the same job may resume its owned directory; changed jobs must use new output
paths. Existing unowned outputs are not silently adopted. This protects local
`refs.pt`, optimizer/checkpoint files and copied outputs from accidental reuse.

Shared teacher and prepared-batch cache roots are further separated under
`release_jobs/<job-sha256>`. This intentionally trades cross-job cache reuse for
unambiguous ownership. Within-job reuse is unchanged. Source/model/capture
immutability still depends on the declared inputs and surrounding execution
contract; a job digest is not a substitute for model-content verification.
No reference values, sample ordering, optimization or loss formulas are changed.

The calibration worker consumes `all_records` as an ordered list of original
request files. The index worker consumes `records`, including original positions.
Requests are decoded with GR00T `MsgSerializer` and must contain `observation`
compatible with the selected policy's preprocessing. The trainer computes BF16
teacher action references before installing quantized layers, then caches them
in `refs.pt`; these are teacher tensors, not a calibrated model checkpoint.
Public capture generation/distribution remains separate from these consumers.


## Build allocation inventory from completed fits

After fitting, supply a build specification whose groups explicitly declare
scope, suite, initialization, K, output directory and exact layer names:

```json
{
  "schema": "sacq_fitted_inventory_build_v1",
  "groups": [
    {
      "scope": "vlm",
      "suite": "shared",
      "init": "aware",
      "k": 16,
      "directory": "/absolute/completed/fits",
      "layers": ["<exact layer name>"]
    }
  ]
}
```

The K and layer shown here illustrate syntax only. Use the actual declared
fitting candidates; no experiment settings are inferred. Each group has one K.
For per-layer K fitting, list those layers in separate corresponding groups.
For DiT use `scope: "dit"` and the exact suite name. Paths follow the original
fitter outputs: `<layer>.pt` for VLM and `<layer>__ck.pt` for DiT.

```bash
python gr00t_libero/bank.py --build-spec /absolute/fitted-groups.json \
  --output-dir /absolute/new/inventory --check-payloads
```

This writes `bank.json` and `inputs.json`; its console output provides the
`bank_manifest` reference for the allocation job. Add the listed file references
to the allocation stage's hashed inputs alongside the job JSON. Missing files
or repeated candidate identities fail; extra directory files are ignored.
`--check-payloads` loads trusted candidate files and verifies K. Without it, the
builder hashes files but does not verify their tensor headers. No directory
scan expands the selected layer set, and no existing inventory is overwritten.
The inventory records file identities; it does not independently prove fitting
completion, candidate coverage against a paper protocol, or scientific approval.


## Use the allocation bank directly for index/calibration jobs

The `jobs.py index` and `jobs.py calibration` build specs accept either an
explicit selected `artifacts` list or the allocation's `bank_manifest`, never
both. For the latter provide:

```json
{
  "bank_manifest": {"path": "/absolute/inventory/bank.json", "sha256": "<digest>"},
  "bank_selection": {"suite": "<exact suite>", "init": "aware"}
}
```

These fields supplement the existing full worker-build specification; they are
not a standalone job or paper preset. The allocation CSV determines each selected
layer's scope and K. The builder selects the matching candidate for the explicit
suite and initialization, checks file hashes, and produces the same worker fields
as the manual-artifact route. A VLM candidate marked `shared` remains eligible;
a DiT candidate from another suite does not. Selected candidates must all exist.
Unused candidates are not opened or added as worker inputs. The manifest itself
and every selected file are registered in the builder's hashed input list.

Scalar/frozen background artifacts still require the explicit `gptq` list: the
builder does not quantize missing background weights or select a new method.
Calibration then substitutes completed index-shard outputs using the existing
coverage and job-identity checks. This connects the sequence:

`fitting outputs → bank.json → allocation CSV → index jobs → completed index shards → calibration job`

The chosen requests, noise, training settings and scientific evidence status are
unchanged by this file-selection automation.


## Build expected results from rollout plans

`results.py` can construct the expected episode manifest directly from an
explicit list of hashed evaluation plans and their hashed task registries:

```json
{
  "schema": "sacq_result_manifest_build_v1",
  "label": "<explicit experimental condition>",
  "aggregation": "episode_micro",
  "plans": [
    {
      "plan": {"path": "/absolute/task-plan.json", "sha256": "<digest>"},
      "tasks": {"path": "/absolute/run/tasks.json", "sha256": "<digest>"}
    }
  ]
}
```

```bash
python gr00t_libero/results.py --build-spec result-plan-list.json --output expected-episodes.json
python gr00t_libero/results.py --manifest expected-episodes.json --output final-summary.json
```

The builder supports the same pinned seed17 worker profile as `jobs.py`; it does
not silently adapt another seed/protocol. It expands each selected task into the
worker's official episode indices 0–49 and exact result paths, with the individual
plan SHA used as `protocol_sha256`. Duplicate task episodes and mixed condition/BPW
plans are rejected. It reads no rollout results and grants no execution approval.
Only supplied plans are expanded: benchmark-wide coverage remains the caller's
explicit scientific scope. Outputs must be new files. Partial aggregation still
requires `--allow-partial` and cannot produce a final success-rate value.


## Explicit index-correction settings

An index build specification must include `job.index_settings`. The exported
worker reads these values at the original numerical call sites; missing values
are rejected. `profiles/legacy_index.json` records the historical worker's values
for inspection, without selecting or authorizing them automatically:

```json
{
  "damping": 0.1,
  "block_columns": 128,
  "noise_seed_base": 7000,
  "moment_chunk_rows": 2048,
  "torch_num_threads": 2,
  "allow_tf32_matmul": true,
  "allow_tf32_cudnn": true
}
```

`block_columns` must be a positive multiple of the supported group size 64.
The per-request action-noise seed remains `noise_seed_base + original_position`.
`moment_chunk_rows` controls input second-moment accumulation chunks; all rows
still contribute. Damping must be finite and positive. Changing these settings
creates a different job identity; numerical/RNG/precision changes require the
corresponding explicit experiment contract and cannot be presented as an
unchanged historical run. This release does not add automatic damping retries.

The standalone numerical solver remains unchanged. The model worker still uses
the pinned GR00T model geometry and device path. Making these settings explicit
is not a claim that arbitrary models or settings have been experimentally tested.


## Check runtime imports without starting a model

After staging the GR00T checkout and installing its external dependencies, run:

```bash
python gr00t_libero/runtime_check.py --workspace /absolute/prepared/workspace --python /absolute/model-environment/bin/python --timeout-seconds 60
```

The probe imports PyTorch, Transformers, the GR00T policy and exported worker
modules in a subprocess with GPU visibility disabled and Hugging Face offline
flags. It requests no model construction, checkpoint loading, forward pass or
simulator rollout. The runtime and its Python modules must be trusted. The
explicit timeout is operational, not a benchmark parameter. It reports
`IMPORTS_PASSED`, `IMPORT_FAILED` or `TIMEOUT_UNVERIFIED`; a timeout is neither a
successful import check nor proof that the dependencies are broken. A pass is
not GPU/end-to-end validation and does not authorize an experiment.

The captured stdout includes flushed JSON progress events (`python_started`,
`import_started`, `import_completed`). If a timeout occurs, the last start event
identifies the import that had not completed. No `python_started` event means
Python startup itself is still unverified. These events locate the observed
stall; they do not diagnose its underlying cause.

For live progress, add `--progress-file /absolute/new/import-progress.jsonl`.
The child flushes every module start/completion event to that file while the
probe runs. Its contents are also included in the final JSON report, including
on timeout. The path must be new; existing logs are not overwritten. This option
does not change the module list, timeout, model behavior or experiment protocol.

On POSIX systems the probe runs in its own process group. Timeout or interruption
terminates that group, including import-created descendants that retain the
group. This prevents an ordinary compile-worker child outliving a timed-out
probe. It does not claim to terminate deliberately detached descendants. On
non-POSIX systems only the immediate subprocess is terminated.
